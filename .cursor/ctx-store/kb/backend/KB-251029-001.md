# How to handle Prisma transaction deadlocks in concurrent order creation?

## Problem
When multiple orders are created simultaneously, Prisma transactions may fail with deadlock errors or timeout issues, especially when updating related records like inventory counts, mart daily metrics, or customer-mart profiles.

## Root Cause
Database deadlocks occur when transactions try to access the same rows in different orders. In the Laundry App, this commonly happens when:
1. Multiple orders update the same mart's `mart_daily_metrics` row
2. Concurrent updates to `customer_mart_profile` totals
3. Inventory updates for the same service items

## Solution

### 1. Use Row-Level Locking with SELECT FOR UPDATE
```javascript
// services/order.service.js
async createOrder(userId, orderData) {
  return await prisma.$transaction(async (tx) => {
    // Lock the customer-mart profile row first
    const profile = await tx.customer_mart_profile.findFirst({
      where: {
        customer_id: userId,
        mart_id: orderData.martId,
      },
      // Add FOR UPDATE to lock the row
      // Note: Use raw query for explicit locking
    });

    // Create order
    const order = await tx.orders.create({
      data: { /* order data */ },
    });

    // Update metrics
    await tx.customer_mart_profile.update({
      where: { profile_id: profile.profile_id },
      data: {
        total_orders: { increment: 1 },
        total_spent: { increment: orderData.totalAmount },
      },
    });

    return order;
  }, {
    maxWait: 5000,  // Max time to wait for transaction to start (5s)
    timeout: 10000, // Max time for transaction to complete (10s)
  });
}
```

### 2. Use Optimistic Concurrency Control
```javascript
// Alternative approach using retry logic
async createOrderWithRetry(userId, orderData, maxRetries = 3) {
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      return await this.createOrder(userId, orderData);
    } catch (error) {
      // Check if it's a deadlock or timeout error
      if (
        (error.code === 'P2034' || // Prisma transaction conflict
         error.message.includes('deadlock') ||
         error.message.includes('timeout')) &&
        attempt < maxRetries
      ) {
        // Exponential backoff
        const delay = Math.min(100 * Math.pow(2, attempt), 1000);
        await new Promise(resolve => setTimeout(resolve, delay));
        logger.warn(`Retry attempt ${attempt} for order creation`, { userId, attempt });
      } else {
        throw error; // Re-throw if not a retryable error
      }
    }
  }
  throw new AppError('Failed to create order after multiple retries', 500);
}
```

### 3. Batch Updates for Metrics (Recommended)
Instead of updating metrics in the same transaction, use a separate background job:

```javascript
// services/order.service.js
async createOrder(userId, orderData) {
  // Main transaction - only essential operations
  const order = await prisma.$transaction(async (tx) => {
    const order = await tx.orders.create({
      data: { /* order data */ },
    });

    await tx.order_items.createMany({
      data: orderData.items,
    });

    await tx.bills.create({
      data: { /* bill data */ },
    });

    return order;
  });

  // Update metrics asynchronously (outside transaction)
  this.updateMetricsAsync(userId, orderData.martId, order.order_id);

  return order;
}

async updateMetricsAsync(userId, martId, orderId) {
  try {
    // These can be updated with retries without blocking order creation
    await prisma.customer_mart_profile.upsert({
      where: {
        customer_id_mart_id: { customer_id: userId, mart_id: martId },
      },
      update: {
        total_orders: { increment: 1 },
        last_order_date: new Date(),
      },
      create: {
        customer_id: userId,
        mart_id: martId,
        total_orders: 1,
        total_spent: 0,
      },
    });
  } catch (error) {
    logger.error('Failed to update metrics', { userId, martId, orderId, error });
    // Don't throw - metrics can be updated later by a cron job
  }
}
```

### 4. Use Database Constraints Instead of Application Logic
```prisma
// prisma/schema.prisma
model customer_mart_profile {
  profile_id     String   @id @default(uuid())
  customer_id    String
  mart_id        String
  total_orders   Int      @default(0)
  total_spent    Decimal  @default(0) @db.Decimal(10, 2)
  
  // Unique constraint prevents duplicate profiles
  @@unique([customer_id, mart_id])
  @@index([customer_id])
  @@index([mart_id])
  @@map("customer_mart_profile")
}
```

### 5. Minimize Transaction Scope
```javascript
// BAD: Long-running transaction
async createOrder(userId, orderData) {
  return await prisma.$transaction(async (tx) => {
    const order = await tx.orders.create({...});
    
    // This might take time - avoid in transaction
    await sendEmailNotification(userId, order); // DON'T DO THIS
    
    // This external API call blocks transaction
    await chargePaymentGateway(order); // DON'T DO THIS
    
    return order;
  });
}

// GOOD: Keep transaction minimal
async createOrder(userId, orderData) {
  // Critical database operations only
  const order = await prisma.$transaction(async (tx) => {
    const order = await tx.orders.create({...});
    await tx.order_items.createMany({...});
    return order;
  });

  // Non-critical operations outside transaction
  await sendEmailNotification(userId, order);
  await chargePaymentGateway(order);
  
  return order;
}
```

### 6. Use Proper Transaction Isolation Level
```javascript
// For critical operations requiring stricter isolation
await prisma.$transaction(
  async (tx) => {
    // Your transaction operations
  },
  {
    isolationLevel: 'Serializable', // Highest isolation level
    maxWait: 5000,
    timeout: 10000,
  }
);
```

## Best Practices

1. **Keep transactions short**: Only include essential operations
2. **Lock in order**: Always acquire locks in the same order to prevent circular deadlocks
3. **Use timeouts**: Set reasonable maxWait and timeout values
4. **Implement retries**: Use exponential backoff for transient failures
5. **Monitor deadlocks**: Log and track deadlock occurrences
6. **Optimize indexes**: Ensure proper indexes on frequently queried/updated columns
7. **Async updates**: Move non-critical updates outside transactions
8. **Connection pooling**: Configure Prisma connection pool appropriately

## Monitoring

```javascript
// Add monitoring for transaction failures
prisma.$use(async (params, next) => {
  const before = Date.now();
  try {
    const result = await next(params);
    const after = Date.now();
    logger.info(`Query ${params.model}.${params.action} took ${after - before}ms`);
    return result;
  } catch (error) {
    const after = Date.now();
    logger.error(`Query ${params.model}.${params.action} failed after ${after - before}ms`, {
      error: error.message,
      code: error.code,
    });
    throw error;
  }
});
```
